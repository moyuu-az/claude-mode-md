# レビュー運用の経緯と実測（参照用）

`~/.claude/CLAUDE.md` のレビュー運用ルールの根拠。ルール本体は CLAUDE.md と
`~/.claude/agents/code-reviewer.md` / `deep-reviewer.md` が SSOT。ここは「なぜそうしたか」の記録。

## 巡回数がコストを支配する (2026-08-22, 業務プロジェクトの PR, 約 5 時間)

| 用途 | 回数 | トークン | 1 回あたり |
| --- | --- | --- | --- |
| Codex レビュー | 4 | 約 16 万 | 約 4 万 |
| Opus レビュー | 2 | 約 34 万 | 約 17 万 |
| Notion 作業記録 | 4 | 約 39 万 | 約 10 万 |

- Codex は tool 呼び出し 1 回で完結するので単価は安い。Opus は 40〜57 回 tool を叩くので 1 回が高い。効くのは単価ではなく回数
- 4 巡かかった原因は巡回の設計。1〜2 巡目は PR が作った欠陥、3〜4 巡目は PR が触れた既存の穴
  （`update()` が読んだ時のエンティティで全列を上書きする構造）。逐次だと 1 巡に 1 つずつしか出ない
- → 1 巡目で「隣接する既存の穴」を聞く／軸で並列に 1 巡してまとめて直す、を運用化

## 隣接コードへ慌てて手を出した事故

3 巡目で隣接コードへ手当てを入れたら、表示の不具合をデータ破壊にすり替えて 4 巡目の BLOCKER になった
（無題の節を返す → 編集画面が `## ` を付けて保存 → 本文の 1 行目が見出しへ移動）。
→ 「隣接の欠陥は指摘し、別 PR にする」に統一。

## 作業ツリー共有による変更消失 (2026-08-22, 同 PR #240)

レビュー agent が 3 ファイルへ `git checkout --` を 19 回かけ、その間に本体が書いていた楽観ロックの実装が消えた。
症状は「テストが実行ごとに違う失敗をする」「`-s` やデバッグ出力を足すと再現しない」。
→ レビュア側で checkout / restore / stash / reset --hard を禁止（エージェント定義に明記）。
依頼前に本体をコミット、書き換え系の作業は `isolation: "worktree"`。

## cold context への切り出し

添付処理の資源上限で独立レビューを 36 巡回しても収束しなかったが、cold context へ切り出して
設計から見直させたところ、36 巡で見つからなかった攻撃を 2 つ塞いだ（784.8MB / 353.3MB のメモリ枯渇経路）。
同じ形の指摘が続くのは、個別ガードの積み増しで隙間が生まれているサイン。

## 依頼先の変遷

以前は「レビュー = Codex」。コストを支配していたのは巡回数で依頼先の単価ではなかったこと、
Codex は認証切れ・auto-deny などの事故要因を抱えることから、既定を SubAgent（code-reviewer）へ変更した。
